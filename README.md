# 🍔 CampusBite: Restaurant Ordering & Delivery Platform

CampusBite is a full-stack food ordering and delivery application for a college campus. **Customers** browse restaurants,
order food with a dummy payment, track their orders, leave reviews, request refunds and get **AI-generated insights**
about their order history. **Restaurant owners** manage menus and orders, assign delivery partners, handle refunds and
see statistics and reminders. **Delivery partners** manage the orders assigned to them.

| Layer | Technology |
|---|---|
| Frontend | React 18 (Vite), JavaScript ES6+, React Hooks (`useState`, `useEffect`, `useContext`, `useMemo`, `useCallback`), React Router DOM v6, Axios |
| Backend | Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2 ORM, JWT (PyJWT), bcrypt |
| Database | PostgreSQL 16 (Docker Compose); SQLite fallback for quick local runs without Docker |
| AI | OpenAI API (Chat Completions, default model `gpt-4o-mini`) |
| DevOps | Docker, Docker Compose, Git & GitHub |

## 1. Features

### 👤 Customer
- Register and log in
- Browse restaurants, with search (by restaurant, cuisine or dish name), a cuisine filter and pagination
- View menus and dish details; search dishes by name and filter by **min/max price**, veg only and sort order
- Cart (one restaurant at a time): add, update quantity, remove, clear. The cart lives in React state and is persisted to localStorage
- Checkout with a **dummy payment** (card / UPI / cash on delivery, all mocked). The order gets `payment_status = mock_paid` and a payment-ledger record
- Customer dashboard: current and past orders with **status and date filters**, pagination, and payment and return status
- Order tracking page with a visual status timeline (auto-refreshes every 15 s while the order is active)
- Cancel an order (only while `PLACED`; the payment is automatically refunded)
- Rate & review after delivery (one review per order)
- Request a return/refund after delivery, with a reason (one request per order)
- **AI order insights**: summaries and free-form questions about your own order history

### 👨‍🍳 Restaurant owner
- Registers together with their restaurant, then edits the restaurant profile (name, cuisine, address, open/closed)
- **Menu management**: add, edit, delete dishes; toggle available/unavailable
- **Order management**: incoming orders, filter by status and date, pagination
- Accept or reject orders and update preparation status (`ACCEPTED → PREPARING → READY`)
- **Assign delivery partners** to `READY` orders (shows each partner's active load)
- **Restaurant statistics**: orders and revenue today and all time, average order value, rating, pending orders, status breakdown, top dishes, 7-day chart
- **Returns & refunds**: approve (status → `REFUNDED`, payment → `refunded`, refund ledger entry) or reject
- **Reminders** for orders left in `PLACED`/`ACCEPTED` for more than 15 minutes (generated by a background task)

### 🛵 Delivery partner
- Sees **only orders assigned to them**, with the customer's name, address and phone
- Filter deliveries by status
- Update status `ASSIGNED → OUT_FOR_DELIVERY → DELIVERED`
- Delivery history with pagination

### Cross-cutting
- JWT authentication with bcrypt password hashing; the token is stored in localStorage and sent as `Authorization: Bearer`
- Role-based access control enforced on the **backend** (every endpoint), plus protected routes and role-based navigation on the frontend
- Strict order state machine: invalid transitions are rejected with **HTTP 409**
- Request validation (Pydantic), meaningful HTTP status codes and error messages
- Logging and response-time middleware
- Responsive UI (desktop and mobile), loading states and error handling everywhere
- Demo data seeded automatically on first start

## 3. Quick start

Requirements: **Docker Desktop** (for the backend) and **Node.js 18+** (for the frontend).

```bash
git clone <your-repo-url> campusbite
cd campusbite

# 1. backend config
cp backend/.env.example backend/.env        # Windows: copy backend\.env.example backend\.env
#    edit backend/.env: set POSTGRES_PASSWORD, JWT_SECRET and (optionally) OPENAI_API_KEY

# 2. backend + database
docker compose --env-file backend/.env up --build

# 3. frontend (new terminal)
cd frontend
cp .env.example .env                        # Windows: copy .env.example .env
npm install
npm run dev
```

Open **http://localhost:5173** and log in with a [demo account](#8-demo-accounts).
API docs: **http://localhost:8000/docs**

## 4. Run the backend with Docker Compose

`docker-compose.yml` starts two containers:

| Service | Image | Port | Purpose |
|---|---|---|---|
| `db` | `postgres:16-alpine` | 5432 | PostgreSQL database (data kept in the `pgdata` volume) |
| `backend` | built from `backend/Dockerfile` | **8000** | FastAPI app (uvicorn) |

```bash
# build and start (from the project root)
docker compose --env-file backend/.env up --build        # add -d to run in the background

docker compose logs -f backend      # follow backend logs (request logging middleware output)
docker compose ps                   # status / health
docker compose down                 # stop
docker compose down -v              # stop AND delete the database volume (fresh start)
```

- `--env-file backend/.env` gives Compose the database credentials, which it uses for the Postgres container and to build the backend's `DATABASE_URL`.
  Without it, Compose falls back to the default credentials `campusbite`/`campusbite`.
- The backend container reads its configuration from `backend/.env` through `env_file`. **Secrets are never baked into the image**
  (`.env` is excluded by `.dockerignore` and `.gitignore`).
- The backend waits for the database health check, then creates the tables and seeds demo data automatically.
- Check it's running: http://localhost:8000/api/health returns `{"status":"ok","database":"postgresql",...}`

## 7. Database setup

**No manual setup is needed.** On startup the backend runs `Base.metadata.create_all()` to create all tables, then
seeds demo data if the `users` table is empty.

- **With Docker (recommended):** PostgreSQL runs in the `db` container; data persists in the `pgdata` volume. Reset it with `docker compose down -v`.
- **Without Docker:** leave `DATABASE_URL` empty to use a local SQLite file (`backend/campusbite.db`), or set it to any
  PostgreSQL URL, e.g. `postgresql+psycopg2://user:pass@localhost:5432/campusbite`.
- Re-seed manually: `python -m app.seed` (inside `backend/`).

### Tables & relationships

| Table | Key columns | Relationships |
|---|---|---|
| `users` | id, name, email (unique), password_hash, role (`customer`/`owner`/`delivery`), phone, address | 1 owner → N restaurants; 1 customer → N orders; 1 delivery partner → N assigned orders |
| `restaurants` | id, owner_id → users, name, cuisine, address, is_open | 1 → N menu_items; 1 → N orders; 1 → N reviews |
| `menu_items` | id, restaurant_id → restaurants, name, price, category, is_veg, is_available | |
| `orders` | id, customer_id → users, restaurant_id → restaurants, delivery_partner_id → users (nullable), status, total_amount, delivery_address, payment_status, return_status, return_reason, created_at, updated_at | 1 → N order_items; 1 → 0..1 review; 1 → N payment_ledger; 1 → N reminder_logs |
| `order_items` | id, order_id → orders, menu_item_id → menu_items (nullable), name & unit_price (snapshot), quantity | |
| `reviews` | id, order_id → orders (**unique**: one review per order), customer_id, restaurant_id, rating 1-5, comment | |
| `payment_ledger` | id, order_id → orders, entry_type (`payment`/`refund`), amount, status (`mock_paid`/`refunded`), method, reference | |
| `reminder_logs` | id, order_id → orders, restaurant_id, status_at_reminder, message, is_resolved | Admin reminder logs |

## 9. Order lifecycle & business rules

```
PLACED → ACCEPTED → PREPARING → READY → ASSIGNED → OUT_FOR_DELIVERY → DELIVERED
   │                                                                     │
   └─→ CANCELLED (customer cancels / owner rejects)       return approved └─→ REFUNDED
```

| Transition | Who | Endpoint |
|---|---|---|
| PLACED → CANCELLED | Customer (only while PLACED) | `POST /api/orders/{id}/cancel` |
| PLACED → ACCEPTED / CANCELLED (reject) | Owner | `PATCH /api/owner/orders/{id}/status` |
| ACCEPTED → PREPARING → READY | Owner | `PATCH /api/owner/orders/{id}/status` |
| READY → ASSIGNED | Owner (picks a delivery partner) | `POST /api/owner/orders/{id}/assign` |
| ASSIGNED → OUT_FOR_DELIVERY → DELIVERED | Assigned delivery partner only | `PATCH /api/delivery/orders/{id}/status` |
| DELIVERED → REFUNDED | Owner approves a return | `POST /api/owner/orders/{id}/return-decision` |

Rules enforced by the backend:
- Any other transition is rejected with **409 Conflict** and a message listing the allowed next statuses.
- Delivered orders cannot be cancelled.
- Prices and totals are always calculated on the server from the database. Unavailable dishes, dishes from another restaurant and closed restaurants are rejected.
- **Dummy payment:** placing an order always "succeeds", sets `payment_status = mock_paid` and writes a `payment` ledger entry with a reference such as `PAY-20250101-1A2B3C4D`.
- Cancelling or rejecting a paid order writes a `refund` ledger entry and sets `payment_status = refunded`.
- **Returns:** only after `DELIVERED`, a reason (≥ 5 characters) is required, and only **one request per order**. Approve → `return_status = approved`, order `REFUNDED`, payment `refunded`, refund ledger entry. Reject → `return_status = rejected`.
- **Reviews:** only after delivery, one per order (unique constraint).

## 10. AI order insights

`POST /api/ai/insights` with `{"question": "..."}` (customers only). The page at **/insights** offers suggested questions:

- *Summarize my last five orders.*
- *Which of my orders are still not delivered?*
- *How much did I spend this week?*
- *Which food items have I ordered most frequently?*

How it works:
1. The backend loads **only the authenticated customer's orders** (`WHERE customer_id = <token user>`), up to 50, newest first.
   The customer ID comes from the JWT, never from the request body, so one customer can't read another customer's data.
2. The orders (date, restaurant, status, items, totals, payment/return status) are sent as JSON context to the OpenAI Chat Completions API,
   with a system prompt instructing the model to answer only from that data.
3. The answer is returned and shown in a chat-style UI.

Error and rate-limit handling:
- A per-customer limit (`AI_RATE_LIMIT_PER_MINUTE`, default 5/min) returns **429** with a `Retry-After` header.
- OpenAI `RateLimitError` → 429; invalid key → 503; timeout or connection errors → 503; other API errors → 502. Each comes with a friendly message.
- The OpenAI client retries transient failures (2 retries, 30 s timeout).
- The API key is read from the `OPENAI_API_KEY` environment variable on the backend only. It's never sent to the browser or committed.
- **No key?** The endpoint still works, using a rule-based offline summary over the same data (marked "Offline insights" in the UI).

## 11. Middleware & background tasks

**Middleware** (`app/middleware.py`): every request is logged with method, path, status code and duration, e.g.
```
INFO campusbite.requests: PATCH /api/owner/orders/12/status -> 200 (8.4 ms) id=3f9a1c2b7d10
```
It also adds `X-Process-Time` and `X-Request-ID` response headers (exposed through CORS).

**Background tasks** (`app/services/reminders.py`):
- An asyncio task started in the FastAPI lifespan scans every `REMINDER_CHECK_SECONDS` for orders still in **`PLACED` or `ACCEPTED`** whose last update is older than **`REMINDER_MINUTES` (15)**.
- For each one it writes a `reminder_logs` record (at most one open reminder per order and status). Reminders resolve automatically once the order moves on, or the owner can dismiss them.
- `GET /api/owner/reminders` also schedules a FastAPI `BackgroundTasks` refresh.
- Reminders appear at the top of the restaurant owner's dashboard (no websockets; the dashboard refreshes every 30 s).

## 13. Security

- Passwords hashed with **bcrypt**; never returned by the API.
- **JWT** (HS256) signed with `JWT_SECRET`, expiring after `JWT_EXPIRE_MINUTES`. The frontend stores it in localStorage and sends it via an Axios interceptor; a 401 clears the session.
- **Backend authorisation on every endpoint:** role dependencies (`require_customer`, `require_owner`, `require_delivery`) plus ownership checks
  (customers see only their own orders, owners only their restaurant's orders and dishes, delivery partners only orders assigned to them).
  Other users' resources return 404.
- Frontend `ProtectedRoute` and role-based navigation, for user experience only; security relies on the backend.
- Server-side price calculation; Pydantic validation on all input.
- Secrets live only in environment variables: `.env` files are excluded from Git (`.gitignore`) and from the Docker image (`.dockerignore`).
  `.env.example` files list the variable names without real values.
- The Docker image runs as a non-root user.

## 15. Troubleshooting

| Problem | Fix |
|---|---|
| Frontend shows "Cannot reach the server at http://localhost:8000" | The backend isn't running: `docker compose --env-file backend/.env up`. Check `docker compose logs backend` |
| CORS error / "Cannot reach the server" while the backend is up | Any `localhost` port is allowed by default. For other hosts add the URL to `CORS_ORIGINS` in `backend/.env` and restart the backend (`docker compose --env-file backend/.env up -d --build`) |
| `password authentication failed` from Postgres | The volume was created with different credentials: `docker compose down -v`, then start again |
| Port 8000 / 5432 / 5173 already in use | Stop the other program, or change the port mapping in `docker-compose.yml` / `vite.config.js` |
| AI says "Offline insights" | `OPENAI_API_KEY` is empty; add it to `backend/.env` and restart the backend container |
| AI returns "invalid API key" | Check the key in `backend/.env` (no quotes or spaces) |
| AI returns "Too many AI requests" | Per-user limit reached; wait a minute or raise `AI_RATE_LIMIT_PER_MINUTE` |
| Want a fresh database with demo data | `docker compose down -v`, then `docker compose --env-file backend/.env up` |
